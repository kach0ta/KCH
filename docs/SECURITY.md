# K.C.H. security notes

## Non-negotiable rule

The server must receive and store ciphertext only. It must not receive message plaintext, encryption keys, recovery phrases, or private identity keys.

## Implemented local encryption primitive

- `Aes256Gcm` uses AES-256-GCM with a 128-bit authentication tag.
- A random 96-bit IV is generated by the Android cryptographic provider for every encryption operation.
- The AES key is generated by Android Keystore and is not exported to app code or uploaded to the API.
- The encoded envelope contains a format version, IV, and authenticated ciphertext. Callers must supply the same associated data when decrypting.
- This key is device-local and is only suitable for protecting data belonging to this installation. It is NOT a conversation key and cannot encrypt messages for another user's device.
- The helper is not yet wired into message sending because the current client has no message composer/send flow. Do not treat messages on the server as end-to-end encrypted.

## What exists elsewhere

- Passwords are not stored in plaintext. The Worker derives a PBKDF2-HMAC-SHA-256 verifier with a per-user random salt and 310,000 iterations.
- Session tokens are generated from a cryptographically secure random source. Only their SHA-256 hashes are stored in D1.
- Sessions expire after 30 days.
- Authenticated conversation reads and writes check conversation membership.
- D1 has a message field named `ciphertext`; a field name does not provide encryption.

## What this does not prove

- There is no implemented client-side conversation key agreement, Signal Protocol session, identity verification, or multi-device protocol.
- Local AES-GCM does not provide end-to-end encryption between users.
- The current cryptographic design has not been independently audited.
- Password hashing does not protect a compromised unlocked device or a compromised account.

## Required before real-world use

1. Integrate and pin a maintained E2EE protocol/library, including its Android native dependencies and license review.
2. Implement client-side identity keys, prekeys, authenticated session establishment, and ratcheting.
3. Define device enrollment, key changes, and safety-number/fingerprint verification.
4. Make message APIs accept and store only authenticated encrypted payloads; reject plaintext.
5. Add rate limiting and abuse controls to registration and login.
6. Add session revocation and device/session management.
7. Review authorization for direct chats, groups, and private channels.
8. Add tests for authentication, membership boundaries, malformed requests, replay handling, and ciphertext limits.
9. Complete an independent security review before describing the messenger as secure or private.

## Operational rules

- Never commit API tokens, passwords, production secrets, private keys, or keystores.
- Keep Cloudflare credentials in local secret storage.
- Do not enable plaintext message logging.
- Do not use this development build for sensitive conversations.
